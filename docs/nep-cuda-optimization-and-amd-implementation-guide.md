# NEP 训练算子优化总结与 AMD 实现建议

**周期：** 2026-09-08—2026-09-11
**代码基线：** `nep-dcu/dev`，截至提交 `3f4b1b3`
**主要案例：** OMat24 `mini_data_test`，FP64，89 种元素，单隐藏层 NEP
**主要实测设备：** NVIDIA RTX 3090、RTX 4090

## 1. 文档目的与使用边界

本轮优化先处理 fitting 网络中大量小 kernel 的调度开销，再处理训练主瓶颈——多体描述符对系数的二阶梯度。结果说明，两类优化都有效，但决定大 batch 能力和完整训练速度的是后者。

本文为 AMD/HIP 优化提供算法、数据布局、性能证据和验证方法。本文不维护 CUDA 与 HIP 的逐文件或逐函数对应关系。两套实现会继续变化，静态映射很容易过期。开始 AMD 工作前，应以当前 HIP 实现为入口，借助代码检索或 Codex 等工具实时比较同一提交中的 CUDA 语义，然后独立选择适合目标 AMD GPU 的实现参数。

所有已合入的新计算路径都保持 FP64。本轮没有使用降低局部精度或低精度 Tensor Core 的方案。

## 2. 结论

- 融合 fitting 后，fitting forward + backward 加速 **15.16 倍**；两轮 epoch 平均耗时下降 **12.90%**。显存峰值只下降约 **0.3%**，最大 batch 没有提高。
- 模板化并融合多体二阶主核后，两轮完整训练中位耗时下降 **84.90%**；设备显存峰值下降 **3422 MiB（60.88%）**。这是本轮最重要的优化。
- fitting 改为运行时 JIT 后解决了静态模板组合过多和重复实现问题，但 RTX 3090 上稳态完整 step 比原 AOT 实现慢 **1.5%～1.7%**，显存不变。JIT 当前主要解决覆盖范围和维护问题。
- 在模板化主核之上，任务展开、c2 融合归约和 `dsnlm_dc` 重算三项连续优化，使完整 step 相对这一轮初始基线在 RTX 3090 上下降 **37.6%**，在 RTX 4090 上下降 **17.2%**；最终再释放约 **323 MiB** PyTorch allocated 峰值。
- AMD 端应优先迁移消除大中间张量和增加主核并行度的算法。线程块宽度、wavefront 使用方式、寄存器目标及 FP64 atomic 策略必须在目标 GPU 上重新测量。

## 4. Fitting 网络融合

### 4.1 原始问题

OMat24 包含 89 种元素，fitting 是很小的单隐藏层网络。逐元素执行时，每个类型都会产生若干小矩阵乘、激活、输入梯度和 scatter kernel。Python 循环、全原子 mask 扫描、数据相关的 `mask.any()` 以及大量小 kernel 共同造成 GPU 调度开销。

第一阶段没有改变原子物理顺序。CPU 数据准备阶段生成按类型分组的原子索引、偏移和计数；融合算子按索引读取 feature，并把结果写回原位置。这样不会改变邻居表、feature 或力计算所依赖的原子编号。

### 4.2 融合计算

对输入 feature `x∈R^D`、隐藏层宽度 `H` 和输出 head 数 `Q`，单元素网络为：

```text
z_j       = b_j + Σ_d x_d W_dj
h_j       = tanh(z_j)
y_q       = c_q + Σ_j h_j V_jq
∂y_q/∂x_d = Σ_j (1 - h_j²) V_jq W_dj
```

融合 forward 同时产生 `y` 和 `∂y/∂x`。训练中的力损失会沿 `∂y/∂x` 对 fitting 参数继续反向传播，因此 backward 还必须实现混合二阶导。只融合推理 forward 或只返回一阶 feature 梯度，不能用于完整力训练。

当前 fitting 约束为：

- FP64；
- 严格单隐藏层，激活为 `tanh`；
- `1 ≤ D ≤ 96`；
- `1 ≤ H ≤ 100`，当前常用配置为 30～100；
- `Q=1` 为普通 NEP，`Q=2` 为 energy/charge 双 head。

feature 数量为：

```text
D = (n_max_radial + 1)
  + (n_max_angular + 1) × l_max_3b
  + [l_max_4b > 0] × (n_max_angular + 1)
  + [l_max_5b > 0] × (n_max_angular + 1)
```

`n_base` 影响描述符基函数展开和系数规模，但不直接进入 fitting 的专用化键。

### 4.3 收益与限制

RTX 3090、256 个结构/2045 个原子的结果：

- fitting forward + backward：80.80 → 5.33 ms，下降 **93.40%**，加速 **15.16 倍**；
- 正式完整 step 中位值：969.54 → 904.70 ms，下降 **6.69%**；
- 两轮 epoch 平均：997.01 → 868.43 s，下降 **12.90%**；
- kernel launch 数量下降 **58.55%**；
- PyTorch peak allocated：601.94 → 600.20 MiB；设备采样峰值只下降 12 MiB；
- 两条路径都在 1793 个结构/15352 个原子时通过，并在 1794 个结构时 OOM。

这说明 fitting 融合主要解决调度和小 kernel 效率，没有消除当时限制 batch 的主要张量。AMD 端应分别测量 fitting 局部耗时和完整 step，不能用局部加速倍数推断训练加速倍数。

## 5. 多体二阶主核：模板展开、融合与寄存器控制

### 5.1 原始瓶颈

profiling 表明，多体描述符对系数的二阶梯度同时是主要耗时和原生显存来源。旧路径先生成按原子、邻居、类型、`n` 和 basis 展开的巨大中间数组，再由后续 kernel 归约。该布局带来：

- 中间数组随原子数、最大邻居数、活跃元素数和描述符阶数乘法增长；
- 大量全局内存写入和再次读取；
- 多次 kernel launch 与同步；
- 单线程持有多组角动量临时数组，寄存器达到 253/thread，并存在溢出风险。

### 5.2 核心方案

专用路径以一个 CTA 处理一个中心原子，先构造当前邻域实际出现的元素类型集合，再分 tile 加载所需数据。中间结果在 CTA 内归并，最终直接写入目标梯度，避免物化完整中间数组。

关键做法：

1. **按实际邻域稀疏性工作。** 不遍历 batch 的全部元素类型，只处理当前中心原子邻域出现的类型。
2. **分阶段复用共享内存。** 不同计算阶段复用同一块共享内存，限制每个 CTA 的占用。
3. **按角动量模板展开。** `L=1,2,3,4` 分别进入独立内联作用域，每次只保留当前 `2L+1` 个分量，缩短临时值生命周期。
4. **数组长度使用真实编译期常量。** `fn/fnp` 等数组使用模型实际长度，不再按全局最大值分配。
5. **避免用寄存器上限掩盖问题。** 通过缩短生命周期和拆分作用域消除 spill，而不是依赖强制 `max register count` 把数据赶到 local memory。
6. **在 CTA 内完成归并。** 只在最终跨中心原子合并时使用必要的全局原子操作。

### 5.3 模板化阶段的结果

OMat24 专用形状为 `n_max_3b=5`、`n_base_3b=9`、`lmax_3=4`，并包含四体、五体项。其他形状继续使用通用路径。

- 稳态 batch：1014.556 → 164.467 ms，下降约 **83.8%**；
- CUDA kernel 总时间：919.229 → 约 81 ms/batch，下降约 **91%**；
- 两轮完整训练中位总耗时：1774.396 → 267.913 s，下降 **84.90%**；
- 设备峰值：5621 → 2199 MiB，下降 **3422 MiB（60.88%）**；
- 原生 allocation 峰值：3.466 → 0.875 GiB，下降 **2.590 GiB**；
- 最终资源检查未出现 local-memory spill。

这一步对 AMD 最有迁移价值：即使暂时不做全部模板展开，先消除巨大中间数组和跨 kernel 往返，也可能同时改善速度与 batch 上限。

## 6. Fitting 运行时 JIT

### 6.1 解决的问题

静态枚举 `D×H×Q×GPU 架构` 会增加编译时间、二进制大小和维护成本。当前 CUDA fitting 改为按实际 `(D,H,Q,SM)` 在运行时生成专用 kernel，并缓存 CUBIN。缓存键还包含 JIT 源码哈希和 NVRTC 版本；并发进程使用文件锁，损坏缓存会在锁内重建。模型移入 GPU 后、DDP 包装前完成预热，因此 epoch 内不重复编译。

支持范围不是一组预先枚举的 `n_max/n_base`：任何产生 `1≤D≤96` 的合法描述符配置，以及 `1≤H≤100`、`Q∈{1,2}` 的网络都可按需生成。`n_base` 不进入 fitting JIT 键。

### 6.2 当前性能

RTX 3090、D=35/H=40：

- AOT 完整 step p50：116.39 ms；
- JIT 冷缓存：118.09 ms，慢 **1.46%**，首次 prepare 为 772.43 ms；
- JIT 热缓存：118.38 ms，慢 **1.72%**，缓存加载为 1.56 ms；
- fitting forward + backward：AOT 6.18 ms，JIT 7.24～7.36 ms，慢约 **17%～19%**；
- 三种模式的 allocated/reserved 峰值相同，均为 599.34/626.00 MiB。

小网络中，Driver API launch、参数准备和生成代码的调度成本占比较高。JIT 的价值是覆盖合法形状并统一维护路径，当前不应宣称它提高了稳态速度。

### 6.3 AMD 端的实现原则

AMD 端可以评估 HIPRTC，但应先回答两个问题：

1. 目标集群上的 HIPRTC 是否能稳定生成并加载目标 `gfx` 架构代码？
2. 对 D≤96/H≤100 的小型 FP64 网络，运行时生成代码是否优于少量代表性静态实现？

建议把 specialization key 设计为至少包含 `(D,H,Q,gfx_arch,HIPRTC版本,源码哈希)`，并把冷编译、热缓存加载和稳态 step 分开报告。先用离线编译探针覆盖最大形状和目标架构，检查编译资源；再接入训练预热、进程内缓存、持久缓存、并发锁和损坏恢复。不要直接假设 NVRTC 的编译选项、module 生命周期或 launch 开销与 HIPRTC 相同。

## 7. 模板主核之后的三项优化

### 7.1 `04bcdbe`：任务从 neighbor 展开为 `(neighbor,n)`

原核每个线程负责一个 neighbor，并在该线程内串行处理全部 `n`。修改后把 `(neighbor,n)` 作为独立任务，显著增加并行度。实际训练中有效邻居数几乎不会低于 7，因此随后在 `d914b95` 移除了没有实际价值的 CTA32 分支，专用路径固定使用 CTA64。

结果：

- RTX 3090 主核：48.670 → 19.303 ms，下降 **60.3%**；完整 step 下降 **34.0%**；
- RTX 4090 主核：25.301 → 10.449 ms，下降 **58.7%**；完整 step 下降 **12.0%**；
- 4090 寄存器 170 → 168/thread，理论 occupancy 16.67% → 25%，实测 active-warps occupancy 14.15% → 22.24%；
- 没有新增大张量，显存基本不变。

AMD 上不要机械采用 64 线程 CTA。CDNA 和 RDNA 的 wavefront 模式、CU 资源和编译器寄存器分配不同。应至少比较一个 wavefront、两个 wavefront及更宽 CTA，并同时观察 kernel 时间、active waves、寄存器、LDS 和尾部任务利用率。

### 7.2 `c6070e9`：融合 c2 计算与归约

原路径先写 c2 二阶导中间张量，再启动 reduce kernel。融合后直接写最终结果，移除中间张量、一次额外 kernel 和两次设备同步。

- RTX 4090 目标路径约 1.29 → 0.163 ms，加速约 **7.9 倍**；
- 完整 step：3090 下降 **3.49%**，4090 下降 **1.54%**；
- GPU kernel 总时间：3090 下降 **8.36%**，4090 下降 **4.28%**；
- memory-event 峰值：3090 约下降 46.2 MiB，4090 约下降 36.2 MiB。

融合可能增加少量 `atomicAdd`，但性能取决于总内存流量和竞争程度，不能只按原子操作数量判断。本例中，减少一次中间张量写回、读取、kernel launch 和同步后的净收益明确为正。AMD 实现应分别测量原子吞吐和地址竞争；优先在寄存器或 LDS 中局部合并，再执行较少的全局 FP64 atomic。

### 7.3 `0de5039`：重算而不是保存稠密 `dsnlm_dc`

优化路径的第一次反向不再写入稠密 `dsnlm_dc`。二阶主核根据当前邻居的实际元素类型，在共享内存中重算所需 tile。通用路径仍保留原实现用于对照和不支持形状。

- 完整 step：3090 再下降 **2.09%**，4090 再下降 **4.41%**；
- peak allocated：3090 下降 322.81 MiB，4090 下降 323.14 MiB；
- peak reserved：两张卡均下降 270 MiB；
- memory-event 峰值：3090 860.30 → 532.30 MiB，4090 847.32 → 510.28 MiB；
- 4090 主核指令数增加约 7.7%、单核时间增加约 1.9%，但完整 step 仍更快。

这是典型的“计算换显存”。对大 batch 训练，应比较重算增加的局部指令与减少的全局读写、allocator 压力和可提升的 batch 上限。单看目标 kernel 时间可能得到错误结论。

## 8. AMD/HIP 优化时必须重新测量的因素

### 8.1 wavefront 与任务映射

- 不把 NVIDIA warp=32 写进算法语义；使用平台提供的 wavefront/warp 宽度信息。
- 分别测试每 CTA 的 wave 数、`(neighbor,n)` 展开顺序和最后一个不完整 tile。
- 观察有效 wave、分支发散和空闲 lane，而不是只看理论 occupancy。

### 8.2 寄存器与 LDS

- 保留“按 L 拆作用域、真实长度数组、分阶段复用共享存储”的原则。
- 用 AMD 编译器资源报告确认 VGPR/SGPR、scratch 和 LDS；scratch 非零通常意味着寄存器溢出。
- 不追求单一 occupancy 数字。寄存器减少如果显著增加指令或 LDS 流量，完整 kernel 可能更慢。

### 8.3 FP64 与原子操作

- 不同 AMD 产品的 FP64 吞吐差异很大，消费级卡与计算卡不能共用性能预期。
- 确认目标架构对 global/LDS FP64 atomic 的支持和生成指令。
- 先做 wave/CTA 内归约，控制落到同一地址的并发写入数量。
- 使用真实 OMat24 类型和邻居分布测竞争，均匀随机 microbenchmark 不足以代表训练。

### 8.4 运行时编译

- 把首次编译、跨进程缓存命中和 epoch 稳态分别计时。
- 缓存键必须包含模型形状、GPU 架构、运行时编译器版本和源码哈希。
- 多 rank 同时启动时需要跨进程锁和原子发布，避免读取未写完的二进制。
- 在正式训练前预热，禁止在计时 epoch 中临时编译。

## 9. 推荐的 AMD 实施顺序

1. **建立基线。** 固定数据顺序、batch、模型、精度、节点和预热次数，记录完整 step、GPU kernel 总时间、目标 kernel、显存峰值和最大 batch。
2. **确认语义。** 从当前 HIP 算子出发，实时比较当前 CUDA 实现，画出输入、输出、保存张量和反向依赖；不要依赖本文维护静态文件映射。
3. **先消除大中间张量。** 优先融合多体二阶路径，避免物化 `dfeat_c3`。这是已知最大速度与显存收益来源。
4. **控制寄存器生命周期。** 按 L 和计算阶段拆分作用域，确认无 scratch/spill 后再调 CTA。
5. **展开 `(neighbor,n)`。** 在目标 GPU 上扫描 CTA/wave 配置，不继承 CUDA CTA64 结论。
6. **融合 c2 与归约。** 比较新增 atomic 与减少全局流量后的净收益。
7. **重算 `dsnlm_dc`。** 在正确性通过后测完整 step、峰值显存和最大 batch，不只测单 kernel。
8. **最后处理 fitting。** 先验证融合算法，再决定使用静态 HIP kernel 还是 HIPRTC。fitting 已不是当前 CUDA 路径的主要瓶颈。

每一步只改变一个因素，并保留可强制选择的基线实现，直到数值、sanitizer 和性能验证完成。

## 10. 验收标准

### 10.1 数值与训练语义

- forward energy/charge 与基线一致；
- `dE/dfeature`、`dQ/dfeature` 与基线一致；
- energy、force、virial、charge/BEC 各损失组合下参数梯度一致；
- 覆盖只有 `grad_y`、只有 `grad_g` 和两者同时存在；
- 一次优化器更新后的参数与基线一致；
- 非默认 stream 正确；
- 单卡和 DDP 均正确；
- 未使用的输出 head 保持 `grad=None` 语义；
- 不规则邻居数、重复元素类型、宽邻居表和空分片均覆盖。

本轮 CUDA 最终测试最大绝对差约 `1.55e-11`。AMD 应根据同一 FP64 参考实现、累加顺序和实际量级制定容差，不能直接照抄一个绝对阈值。

### 10.2 内存与并发安全

- 记录框架 allocator 的 allocated/reserved 峰值；
- 同时记录进程设备显存或 runtime memory event，覆盖框架之外的原生分配；
- 检查越界、未初始化读取、竞争和 stream 顺序；
- 扫描 batch 上限，并记录 OOM 前最后一个成功 batch 的结构数和原子数。

### 10.3 性能

- 相同节点、相同 GPU 时钟策略、相同 batch 序列和相同预热；
- 报告 p50 和 p95，不只报告最佳值；
- 同时报告完整 step、GPU kernel 总时间和目标 kernel；
- 完整 epoch 只用于最终确认；
- JIT 必须分开报告冷缓存、热缓存和稳态；
- profiler 自身开销不能与普通训练日志直接比较。
